Observability means being able to see what your app is doing in production: which errors
happen, which requests are slow and why, and what the logs said at the time.

Suku does not ship this as a package. The CLI writes it into your project as ordinary code
you own, the same way it does for [logging](/docs/logging#pino-and-opentelemetry).

## Pick a vendor

There are two drivers. **Sentry** has its own SDK. Everything else speaks **OpenTelemetry**'s
protocol (OTLP), so one driver serves all of them and the vendor you pick only decides the
example values written to `.env.example`.

| Vendor                         | `--observability`           | Driver        | Notes                                                               |
| ------------------------------ | --------------------------- | ------------- | ------------------------------------------------------------------- |
| Sentry                         | `sentry`                    | Sentry        | Also self-hosted Sentry.                                            |
| GlitchTip                      | `glitchtip`                 | Sentry        | Open source. Uses the Sentry SDK with its own DSN.                  |
| Any OTLP endpoint or collector | `opentelemetry` (or `otel`) | OpenTelemetry |                                                                     |
| Grafana Cloud                  | `grafana`                   | OpenTelemetry |                                                                     |
| Honeycomb                      | `honeycomb`                 | OpenTelemetry |                                                                     |
| SigNoz                         | `signoz`                    | OpenTelemetry | Cloud or self-hosted.                                               |
| Jaeger                         | `jaeger`                    | OpenTelemetry | Traces only: logs and metrics are switched off.                     |
| Axiom                          | `axiom`                     | OpenTelemetry | Metrics are switched off: Axiom takes them in a separate dataset.   |
| New Relic                      | `newrelic`                  | OpenTelemetry |                                                                     |
| Datadog                        | `datadog`                   | OpenTelemetry | Through the Datadog Agent on the same host, with OTLP ingestion on. |

Datadog and New Relic also have their own agents. Those work by changing libraries as they
load, which does not work in the single file `suku build` produces, so they are reached
through OpenTelemetry here.

## Add it

To a new project:

```bash
suku new my-api --observability sentry
```

In a terminal, `suku new` also asks. The default is none.

To a project you already have:

```bash
suku generate observability honeycomb
bun install
```

Both give the same result. Then set the variables from `.env.example` where the app runs.
**Without them nothing is sent and the SDK is never started**, which is how development and
tests run.

  <Tab value="Sentry">
    ```bash title=".env.example"
    # Sentry is off until SENTRY_DSN is set.
    SENTRY_DSN=
    SENTRY_ENVIRONMENT=production
    ```
  </Tab>
  <Tab value="OpenTelemetry (Honeycomb shown)">
    ```bash title=".env.example"
    # Honeycomb is off until OTEL_EXPORTER_OTLP_ENDPOINT is set.
    # EU accounts use https://api.eu1.honeycomb.io.
    # OTEL_EXPORTER_OTLP_ENDPOINT=https://api.honeycomb.io
    # OTEL_EXPORTER_OTLP_HEADERS=x-honeycomb-team=<api key>
    OTEL_SERVICE_NAME=my-api
    APP_ENV=production
    ```
  </Tab>
  <Tab value="Grafana Cloud">
    ```bash title=".env.example"
    # Grafana Cloud is off until OTEL_EXPORTER_OTLP_ENDPOINT is set.
    # OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp-gateway-<zone>.grafana.net/otlp
    # OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<base64 of instance-id:token>
    OTEL_SERVICE_NAME=my-api
    APP_ENV=production
    ```
  </Tab>
</Tabs>

For OpenTelemetry, remove the `#` and fill in the values. `OTEL_EXPORTER_OTLP_HEADERS` is
where the API key goes, as `name=value` pairs separated by commas. Write a space inside a
value as `%20`, as in `Authorization=Bearer%20<token>`.

<Callout title="Check the values with your vendor">
  The endpoints and header names in `.env.example` are examples. Regions and plans differ, so copy
  the exact values from your vendor's OpenTelemetry page.
</Callout>

## What gets sent

| Signal  | What you see                                                   | Where it comes from            |
| ------- | -------------------------------------------------------------- | ------------------------------ |
| Errors  | Every error nobody handled, with its stack and the route       | `onError: reportError`         |
| Traces  | One trace per request, named after the route: `GET /users/:id` | The `Observability` middleware |
| Spans   | The time spent in a method you marked                          | `@Traced()`                    |
| Logs    | Every line your `Logger` writes                                | One line in `src/logger.ts`    |
| Runtime | Memory, CPU time, uptime and event-loop delay                  | The driver                     |

A `404`, a `400` or any other [`HttpException`](/docs/errors) is an answer your app chose to
give, so it is not reported as an error.

When a request arrives as part of a trace another service started (a `traceparent` header),
the trace continues: your spans join the caller's.

## What the CLI adds

```text
src/
  instrument.ts                    # the settings; main.ts imports it first
  observability/
    index.ts                       # what your code imports
    init.ts                        # starts the vendor
    telemetry.ts                   # picks the driver; exports `telemetry`
    observability.types.ts         # ObservabilityOptions, Telemetry
    observability.middleware.ts    # Observability, reportError
    traced.decorator.ts            # @Traced()
    drivers/
      sentry/  or  otel/           # the only folder that imports a vendor's SDK
        init.ts
        driver.ts
```

The SDK goes into your `package.json`: `@sentry/node` (`@sentry/bun` when the project's
runtime is Bun), or the `@opentelemetry/*` packages.

It also edits three existing files. In `src/main.ts`, the import, the middleware and the
error handler:

```ts title="src/main.ts"
import './instrument'; // must stay the first import

import { Logger, singleton, Suku } from '@sukujs/core';
import { nodeAdapter } from '@sukujs/platform-node';
import { securityHeaders } from '@sukujs/security';
import { AppFeature } from './app.feature';
import { Env } from './config';
import { PinoLogger, requestLogger } from './logger';
import { Observability, reportError } from './observability';

const app = await Suku.create({
  features: [Env.load(), AppFeature],
  // Replaces the built-in console logger: every `Logger` in the app now writes through pino.
  services: [singleton(Logger, PinoLogger)],
  // Defensive headers on every response, including 404s and errors.
  middlewares: [Observability, requestLogger, securityHeaders()],
  onError: reportError,
  adapter: nodeAdapter(),
});
```

In `src/logger.ts`, one line that sends each log line on:

```ts title="src/logger.ts"
log(level: LogLevel, message: string, meta?: Record<string, unknown>): void {
  this.pino[level](meta ?? {}, message);
  telemetry.log(level, message, meta);
}
```

And the variables in `.env.example`.

<Callout type="warn" title="Two things that must stay first">
  `import './instrument'` must stay the first line of `src/main.ts`, so the SDK is running before
  the server starts. `Observability` must stay the first middleware, so everything else, including
  the request log, happens inside the trace.
</Callout>

If the generator cannot make one of these edits safely, for example because your `main.ts`
already has an `onError`, it changes nothing there and prints a note that says what to add.

## Settings

Everything you are likely to change is in one file.

<Tabs items={['Sentry', 'OpenTelemetry']}>
  <Tab value="Sentry">
    ```ts title="src/instrument.ts"
    // Starts error and performance reporting. `main.ts` imports this file first, before anything
    // else loads, and it must stay that way.
    import { initObservability } from './observability/init';

    initObservability({
      dsn: process.env.SENTRY_DSN,
      // On only when a DSN is set, so development and tests send nothing.
      enabled: Boolean(process.env.SENTRY_DSN),
      environment: process.env.SENTRY_ENVIRONMENT,
      // One request in ten is traced. Errors are always reported.
      traceSampleRate: 0.1,
      // A request with this header set to "1" is always traced, which helps when debugging.
      forceTraceHeader: 'x-app-trace',
    });
    ```

  </Tab>
  <Tab value="OpenTelemetry">
    ```ts title="src/instrument.ts"
    // Starts tracing, log shipping and metrics. `main.ts` imports this file first, before anything
    // else loads, and it must stay that way.
    import { initObservability } from './observability/init';

    // A collector, or your vendor's OTLP endpoint. An API key goes in OTEL_EXPORTER_OTLP_HEADERS,
    // which the exporters read themselves.
    const endpoint = process.env.OTEL_EXPORTER_OTLP_ENDPOINT;

    initObservability({
      dsn: endpoint,
      // On only when an endpoint is set, so development and tests send nothing.
      enabled: Boolean(endpoint),
      serviceName: process.env.OTEL_SERVICE_NAME ?? 'my-api',
      environment: process.env.APP_ENV,
      // One request in ten is traced. Errors are always reported.
      traceSampleRate: 0.1,
      // A request with this header set to "1" is always traced, which helps when debugging.
      forceTraceHeader: 'x-app-trace',
    });
    ```

  </Tab>
</Tabs>

| Option             | What it does                                                                    |
| ------------------ | ------------------------------------------------------------------------------- |
| `dsn`              | Where the data goes: a Sentry DSN, or an OTLP endpoint.                         |
| `enabled`          | Off means the SDK is not started at all.                                        |
| `serviceName`      | The name your app is listed under. OpenTelemetry only.                          |
| `environment`      | `production`, `staging` and so on. Shown next to every error and trace.         |
| `traceSampleRate`  | The share of requests that are traced, from `0` to `1`. Errors are always sent. |
| `forceTraceHeader` | A request with this header set to `1` is always traced.                         |
| `ignoreTraces`     | Names of traces that are never sent, as regular expressions.                    |
| `ignoreError`      | Return `true` for an error that should not be reported.                         |
| `logs`             | `false` stops sending log lines. Default `true`.                                |
| `runtimeMetrics`   | `false` stops sending memory and CPU figures. Default `true`.                   |

Tracing every request costs quota, so only one in ten is traced by default. When you are
chasing one slow request, send the header and that request is traced for certain:

```bash
curl -H 'x-app-trace: 1' https://api.example.com/users/42
```

<Callout type="warn" title="Do not use NODE_ENV here">
  `suku build` replaces `process.env.NODE_ENV` with a fixed value while it bundles, so a check such
  as `enabled: process.env.NODE_ENV === 'production'` is decided at build time, not when the app
  starts. That is why the switch is the DSN or the endpoint.
</Callout>

## Use it in your code

Import from `./observability`, never from a vendor's package.

**Time a method.** `@Traced()` records a span named `Class.method` inside the trace of the
request that called it.

```ts
import { Service } from '@sukujs/core';
import { Traced } from '../observability';

@Service()
export class ReportsService {
  @Traced()
  async build(month: string) {
    // ...
  }
}
```

**Report an error you handled.** Unhandled errors are reported for you. One you caught is
not, unless you say so.

```ts
import { telemetry } from '../observability';

try {
  await payments.charge(order);
} catch (error) {
  telemetry.captureException(error, { orderId: order.id });
  return { status: 'retrying' };
}
```

**Time a block of code** that is not a whole method.

```ts
const rows = await telemetry.startSpan({ name: 'load report rows', op: 'db' }, () =>
  db.reports.forMonth(month),
);
```

**Log** the usual way. Ask for [`Logger`](/docs/logging) and write to it; the lines are sent
on as well.

<Callout type="warn" title="Never send secrets or personal data">
  Log and report ids and outcomes: `orderId`, `status`, `durationMs`. Never tokens, passwords,
  one-time codes, emails, phone numbers or payment details.
</Callout>

## Shutting down

`Observability` is created by the container, so it is [disposed](/docs/dependency-injection#disposal)
when the app closes. That is when it sends whatever is still waiting. The starter's
`src/main.ts` already calls `app.close()` on `SIGTERM`, so nothing is lost on a deploy.

## Limits

For both drivers:

- **Database and HTTP client calls are not traced automatically.** Vendors do that by changing
  those libraries as they load, which does not work in the single file `suku build` produces.
  Use `@Traced()` or `telemetry.startSpan` around the calls you care about.
- **The Cloudflare Workers and Vercel entry points are not wired.** `suku new` sets this up
  in `src/main.ts` only.

With Sentry:

- **On Bun, Sentry prints one warning at start** about library patching. Errors, traces, logs
  and `@Traced()` still work.
- **A Node project under `suku dev` sends no request traces**, because `suku dev` runs it with
  Bun and the Node SDK cannot see Bun's server. Errors and logs still arrive. The built app
  on Node traces normally.
- **The JSON logs on stdout do not carry Sentry's trace ids.** The copies sent to Sentry are
  linked to their trace.

With OpenTelemetry:

- **Errors arrive as an exception on their span and as an error log**, not in an inbox of
  their own. Whether you get grouping and alerts for them depends on the vendor.
- **An unhandled error produces two error log lines**: the report itself, with the stack, and
  the line your `Logger` writes for it.
- **The JSON logs on stdout do carry the trace ids** (`trace_id`, `span_id`), the same ones
  the vendor shows.

## Another vendor

Your code only knows the `Telemetry` interface, so changing vendor does not touch it.

- **To another OpenTelemetry vendor:** change the variables. No code changes.
- **Between Sentry and OpenTelemetry:** delete `src/observability` and `src/instrument.ts`,
  then run `suku generate observability <vendor>` again.
- **To a vendor with its own SDK:** add `src/observability/drivers/<vendor>/` with an
  `init.ts` and a `driver.ts` that implements `Telemetry`, and point `init.ts` and
  `telemetry.ts` at it.
